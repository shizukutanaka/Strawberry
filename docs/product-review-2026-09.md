# 長所・短所・改善点の洗い出し（2026-09）

イーロン・マスクのアルゴリズム（①要件を疑う ②削除する ③単純化する ④加速する ⑤自動化する）と、
ソクラテス的な問い詰めでこの製品を点検した記録。**主張を一つ選び、それが本当かを
コードで確かめる**やり方で進めた。以下の事実はすべてコードを読んで確認したもので、
推測は「未確認」と明記する。

---

## 起点の問い

この製品が最も強く主張していたのは次の一文だった。

> 帳簿は 3 つの不変条件で自動突き合わせされる（`src/payments/reconciliation.js`）。
> 保存則・取りこぼしゼロ・出所のない計上ゼロ。

**問: その不変条件は「金」を見ているのか、「記録」を見ているのか。**

答えは記録だった。`reconcile()` が読むのは `PaymentRepository` と `LedgerRepository` の
2 つだけである。台帳に行を書かずに送金する経路があれば、その金はどの不変条件からも
永久に見えない。そして、そうした経路は 3 本あった。

---

## 長所（疑って、残ると判断したもの）

1. **できないことを実装済みと書かない文化。** 台帳のコメントは「運営が送金しなければ
   資金は動かない（信頼が要る）」と明記し、アテステーションは Mock だと言い切っている。
   この製品の最大の資産であり、今回の点検が成立したのもこの文化のおかげ
   （嘘が書いてあったのは 2 箇所だけで、どちらも「配線済」の誤認だった）。
2. **導出する残高。** 残高を保存せず仕訳の合計から導く（`payout-ledger.balanceFor`）。
   「壊れた残高」という状態が存在し得ない。
3. **観測して埋める設計。** `earnings-sweeper` は完了経路 5 つにフックを刺さず、状態を
   後から観測して計上する。6 つ目の経路が増えてもプロバイダが無給にならない。
4. **知らないものに数字を付けない。** `perf-score` は参照表に無い型番のスコアを推測せず
   `null` を返し、申告 TFLOPS を消費電力由来の物理上限でクランプする。今回この判定を
   価格側にも通した（`quoteGpu` の `basis.quotable`）。
5. **機械的な検査を積んできたこと。** 全ルート走査・ドキュメント照合・帳簿の突き合わせ。
   ただし後述のとおり、**検査範囲の外にある物は検査できない**——この点検の主題そのもの。

## 短所（今回対処したもの）

### A. 決済スタックが 2 系統あり、片方は二重払いを生んでいた

`POST /payment/btc`（btc-onchain、244 行）について確認した事実:

| 主張 | 実態 |
|---|---|
| オンチェーン BTC 決済である | ❌ `sendBTC` は Lightning API を呼ぶだけだった |
| 製品の決済経路である | ❌ UI からは一度も呼ばれていなかった |
| 台帳を通らない（仕様書の 🟡） | ✅ 正しいが、影響は書かれていたより重い |

支払い時点で——GPU 起動前に——プロバイダへ全額を送っていた。従量按分・SLA ペナルティ・
係争返金・Spot 中断按分をすべて迂回する。さらにその送金は台帳に行を書かないため、
注文完了時に `payout-ledger` が**もう一度**同額を計上した。プロバイダは送金と台帳残高の
両方を受け取れた。それでも 3 つの不変条件はすべて healthy を返した。
**帳簿は合っていた。合っていなかったのは現金である。**

手数料の取り方も上乗せ式で、Lightning 経路の控除式と逆だった。同じ注文が経路によって
値段の違うものになっていた（借り手に 1.5% 高く、プロバイダに 1.5% 多く）。

→ **削除**。`lightning-api.js`・`btc-payment.js` の大半・`selectProfitAddress` が
連鎖して呼び出し元を失い、あわせて撤去した。

### B. 同じ穴が生の BOLT11 パススルーに 2 本残っていた

再発防止のガードを書いたとき、**消したばかりの API 名を手で並べた**ので、生きている
送金経路を見逃した。`lightning.payInvoice()` を直接叩く `POST /payment` と
`POST /payments/pay` である。admin 限定で上限束縛などの防御はあったが、
**送金しても台帳の payout 行を書かない**という一点で btc-onchain と同じだった。
送っても残高が減らないので、プロバイダは同じ額をもう一度申請できた。

→ **削除**し、外部へ資金が出る経路を `POST /payments/admin/payouts/:id/complete`
一本に集約した。出金申請の行が無ければ送れない。
ガードは列挙をやめ、**ソースから導出する**ようにした（送金を意味するメソッド名を
全部拾う）。書き換えた途端 3 つ目の候補 `action-executor.js` を検出し、
本番の `createEscrowService()` が 5 箇所すべて `lnAdapter` を渡していない事実を
検査で固定した。

### C. 目的が消えたのに入口だけ残っていた（peerId）

PeerID は libp2p 上の身元で、それを使う P2P レイヤは既に削除済み。読む側は
アクセス監査ログの 1 行だけ。149 人のユーザーのうち設定した者はゼロ。→ **削除**。

### D. 価格エンジンが値段を一つも決めていなかった

`feature-pricer` は実装もテストも揃い `POST /marketplace/quote` として登録もされて
いたが、UI からは一度も呼ばれず、`openOrderEscrow` も見積額を注文の `totalPrice` で
上書きしていた。一方で貸し手が値段を勘で決めているのは実在の欠落だった。
→ **削除ではなく結線**。出品フォームの参考価格として出す。ただし参照表で型番が
特定できたときだけ（未知型番でも VRAM だけで数字が出てしまうため）。

### E. README の約 4 割が製品の説明ではなかった

925 行のうち、どのプロジェクトにも当てはまる一般論（「AI 月次レポート」「グローバル展開
Tips」）か、この製品に無い機能の説明（「ノード追加/削除の自律運用」「PagerDuty/Jira への
自動チケット発行」）が約 4 割を占めていた。「ノード障害時も他ノードから再同期可能」に
至っては、単一サーバ構成であることを同じ README の別の場所が書いていた。

決定的だったのは実行できない手順である。`node src/cli.js`・`node src/p2p-notify.js` は
どちらもファイルが存在せず、`npm run start:prometheus` / `monitor:nodes` /
`report:monthly` は package.json に 1 つも無い。手順どおりに叩いた人には
「動かない」としか分からない。

→ **309 行に整理**。「できること／できないこと」を並べて書く節を新設し、
送金が人の操作であること・アテステーションが Mock であること・hold invoice が
未結線であることを、探さなくても目に入る位置に置いた。
`npm run ...` の実在は `tests/docs/docs-match-code.test.js` が機械的に確かめる。

## 短所（未対処。正直に書き残す）

1. **実送金は運営の手作業のまま**（`{paymentRequest}` を渡せばサーバが払うが、
   出金申請ごとに人が実行する）。完全自動化には運用上の判断が要る。
2. **アテステーション検証は Mock**（nvtrust 未実装）。文書は正確で、過大主張はない。
3. **hold invoice エスクローは未結線。** `escrow-state-machine` は純関数として完成して
   いるが、本番で `lnAdapter` は渡されない。ARCHITECTURE.md がこれを「解決済み」と
   書いていたのは誤りだったので訂正した（呼ばれてはいるが、即 return していた）。
4. **JSON データ層に複数レコードのトランザクションが無い。** 台帳の二重計上は
   `createUnique` の原子性で防いでいるが、一般解ではない。
5. **製品から到達しないエンドポイントが 37 本**（admin・インフラ系を除く）。
   すべてが誤りではない（プログラマティックな API 面として意図的なものもある）が、
   増やさないためにラチェットを置いた（`tests/api/ui-reachability.test.js`）。

## 改善点（この点検で入れた恒久的な仕掛け）

| 仕掛け | 何を止めるか |
|---|---|
| `tests/payments/no-unledgered-money.test.js` | 台帳に行を書かない送金。送金メソッドの一覧を**ソースから導出**する |
| `reconciliation` の `noUnbackedPayouts` | 台帳に「送った」とあるのに txid が無い出金 |
| `reconciliation` の `unattributedPaidSats` | 注文に紐づかない入金を黙って捨てないこと |
| `tests/api/ui-reachability.test.js` | 製品から到達しないエンドポイントが増えること（ラチェット） |
| `quoteGpu` の `basis.quotable` | 根拠の無い型番に値段を付けて人に見せること |
| `docs-match-code` の npm script 検査 | 実行できない手順をドキュメントに書くこと |

既存の `no-dead-endpoints` は「叩けば応答するか」を、新しい `ui-reachability` は
「そもそも誰かが叩くのか」を見る。応答するが誰も呼ばないエンドポイントは、
動くことをテストで確かめられている分だけ、壊れた機能より見つけにくい。

## この点検から得た一般則

1. **不変条件は、それが読む範囲の外を守れない。** 帳簿の突き合わせは帳簿しか見ない。
   金を守りたいなら「金が動く経路」の側を構造的に狭める必要がある。
2. **列挙は必ず古くなる。** 再発防止の検査を書くときに、消したばかりのものを手で
   並べてはいけない。導出できる形にしないと、書いたその日から漏れる。
   （この文書の B 節はその失敗の記録である。）
3. **「呼ばれている」と「実行されている」は違う。** `executeActions()` は呼ばれていたが、
   `lnAdapter` が無いので即 return していた。呼び出しの存在を配線の証拠にしない。
4. **削除は連鎖する。** 1 本のルートを消すと、そのために存在していた 3 モジュールが
   呼び出し元を失った。②を飛ばして③以降をやると、この連鎖が起きない。

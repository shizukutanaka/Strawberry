# 長所・短所・改善点の洗い出し（2026-09）

イーロン・マスクのアルゴリズム（①要件を疑う ②削除する ③単純化する ④加速する ⑤自動化する）と、
ソクラテス的な問い詰めでこの製品を点検した記録。**主張を一つ選び、それが本当かを
コードで確かめる**やり方で進めた。以下の事実はすべてコードを読んで確認したもので、
推測は「未確認」と明記する。

---

## 起点の問い

この製品が最も強く主張していたのは次の一文だった。

> 帳簿は 3 つの不変条件で自動突き合わせされる（`src/payments/reconciliation.js`）。
> 保存則・取りこぼしゼロ・出所のない計上ゼロ。

**問: その不変条件は「金」を見ているのか、「記録」を見ているのか。**

答えは記録だった。`reconcile()` が読むのは `PaymentRepository` と `LedgerRepository` の
2 つだけである。台帳に行を書かずに送金する経路があれば、その金はどの不変条件からも
永久に見えない。そして、そうした経路は 3 本あった。

## 長所（疑って、残ると判断したもの）

1. **できないことを実装済みと書かない文化。** 台帳のコメントは「運営が送金しなければ
   資金は動かない（信頼が要る）」と明記し、アテステーションは Mock だと言い切っている。
   この製品の最大の資産であり、今回の点検が成立したのもこの文化のおかげ
   （嘘が書いてあったのは 2 箇所だけで、どちらも「配線済」の誤認だった）。
2. **導出する残高。** 残高を保存せず仕訳の合計から導く（`payout-ledger.balanceFor`）。
   「壊れた残高」という状態が存在し得ない。
3. **観測して埋める設計。** `earnings-sweeper` は完了経路 5 つにフックを刺さず、状態を
   後から観測して計上する。6 つ目の経路が増えてもプロバイダが無給にならない。
4. **知らないものに数字を付けない。** `perf-score` は参照表に無い型番のスコアを推測せず
   `null` を返し、申告 TFLOPS を消費電力由来の物理上限でクランプする。今回この判定を
   価格側にも通した（`quoteGpu` の `basis.quotable`）。
5. **機械的な検査を積んできたこと。** 全ルート走査・ドキュメント照合・帳簿の突き合わせ。
   ただし後述のとおり、**検査範囲の外にある物は検査できない**——この点検の主題そのもの。

## 短所（今回対処したもの）

### A. 決済スタックが 2 系統あり、片方は二重払いを生んでいた

`POST /payment/btc`（btc-onchain、244 行）について確認した事実:

| 主張 | 実態 |
|---|---|
| オンチェーン BTC 決済である | ❌ `sendBTC` は Lightning API を呼ぶだけだった |
| 製品の決済経路である | ❌ UI からは一度も呼ばれていなかった |
| 台帳を通らない（仕様書の 🟡） | ✅ 正しいが、影響は書かれていたより重い |

支払い時点で——GPU 起動前に——プロバイダへ全額を送っていた。従量按分・SLA ペナルティ・
係争返金・Spot 中断按分をすべて迂回する。さらにその送金は台帳に行を書かないため、
注文完了時に `payout-ledger` が**もう一度**同額を計上した。プロバイダは送金と台帳残高の
両方を受け取れた。それでも 3 つの不変条件はすべて healthy を返した。
**帳簿は合っていた。合っていなかったのは現金である。**

手数料の取り方も上乗せ式で、Lightning 経路の控除式と逆だった。同じ注文が経路によって
値段の違うものになっていた（借り手に 1.5% 高く、プロバイダに 1.5% 多く）。

→ **削除**。`lightning-api.js`・`btc-payment.js` の大半・`selectProfitAddress` が
連鎖して呼び出し元を失い、あわせて撤去した。

### B. 同じ穴が生の BOLT11 パススルーに 2 本残っていた

再発防止のガードを書いたとき、**消したばかりの API 名を手で並べた**ので、生きている
送金経路を見逃した。`lightning.payInvoice()` を直接叩く `POST /payment` と
`POST /payments/pay` である。admin 限定で上限束縛などの防御はあったが、
**送金しても台帳の payout 行を書かない**という一点で btc-onchain と同じだった。
送っても残高が減らないので、プロバイダは同じ額をもう一度申請できた。

→ **削除**し、外部へ資金が出る経路を `POST /payments/admin/payouts/:id/complete`
一本に集約した。出金申請の行が無ければ送れない。
ガードは列挙をやめ、**ソースから導出する**ようにした（送金を意味するメソッド名を
全部拾う）。書き換えた途端 3 つ目の候補 `action-executor.js` を検出し、
本番の `createEscrowService()` が 5 箇所すべて `lnAdapter` を渡していない事実を
検査で固定した。

### C. 目的が消えたのに入口だけ残っていた（peerId）

PeerID は libp2p 上の身元で、それを使う P2P レイヤは既に削除済み。読む側は
アクセス監査ログの 1 行だけ。149 人のユーザーのうち設定した者はゼロ。→ **削除**。

### D. 価格エンジンが値段を一つも決めていなかった

`feature-pricer` は実装もテストも揃い `POST /marketplace/quote` として登録もされて
いたが、UI からは一度も呼ばれず、`openOrderEscrow` も見積額を注文の `totalPrice` で
上書きしていた。一方で貸し手が値段を勘で決めているのは実在の欠落だった。
→ **削除ではなく結線**。出品フォームの参考価格として出す。ただし参照表で型番が
特定できたときだけ（未知型番でも VRAM だけで数字が出てしまうため）。

### E. README の約 4 割が製品の説明ではなかった

925 行のうち、どのプロジェクトにも当てはまる一般論（「AI 月次レポート」「グローバル展開
Tips」）か、この製品に無い機能の説明（「ノード追加/削除の自律運用」「PagerDuty/Jira への
自動チケット発行」）が約 4 割を占めていた。「ノード障害時も他ノードから再同期可能」に
至っては、単一サーバ構成であることを同じ README の別の場所が書いていた。

決定的だったのは実行できない手順である。`node src/cli.js`・`node src/p2p-notify.js` は

### F. 「動く」と「使われる」は別だった — 到達しない 37 本の個別審査（第 2 回）

第 1 回で置いたラチェット（37 本を上限に固定）は「増やさない」だけだった。
第 2 回はその 37 本を一件ずつ問い詰めた。判定は「UI から呼ぶ理由があるか」ではなく
「**この要件は成立しているか**」（マスク①→②）。

| 判定 | 本数 | 内訳 |
|---|---|---|
| **削除** | 16 | 見積・資格事前チェック・カレンダー/手動ブロック・注文履歴・使用状況・一括登録・複製・rank・stats・汎用インボイス・インボイス照会・支払い履歴・settings・activity |
| **画面に配線** | 10 | refresh / logout、パスワード変更、通知先 ×3、ウォッチ一覧、出品者の信頼度、借り手の信頼度、借り手への評価 |
| **再分類** | 11 | admin ロールでしか通れないもの（ミドルウェアの印から機械的に判定）と、第三者検証用の `/audit-anchors` |

問い詰めて初めて見えた欠陥（ラチェットを置いただけでは永久に見えなかったもの）:

- **1 時間で強制ログアウト。** UI はログイン応答の refreshToken を捨てていた。数時間の
  GPU 利用中に必ず 401 → ログイン画面へ。サーバの refresh ローテーション・reuse 検知は
  丁寧に実装されテストされていたが、製品からは一度も呼ばれていなかった
- **「ログアウト」が localStorage を消すだけ。** コピーされたトークンは期限まで有効。
  サーバ側の失効 API は存在したが呼ばれていなかった
- **貸し手への通知が一度も発火していなかった。** 通知先を登録する画面が無かった
- **汎用インボイス（admin）は支払われてもどの記録にも残らなかった。** 文書は
  「`unattributedPaidSats` に現れる」と書いていたが、`PaymentRepository` に行を書いて
  いなかった。A の「帳簿に映らない金」と同じ種類の穴が、まだ 1 本残っていた
- **借り手の評価計算が 2 箇所にあり、片方だけバグが直っていた。** 注文詳細は無効な
  評価値を ★1 に丸めて平均に混ぜていた（renter-profile 側で直した同じバグ）
- **パスワード変更直後の再ログインが同じ秒内だと失敗する。** 配線して E2E を書いた
  ことで初めて再現した
- **通知先の GET/POST が往復できない。** 伏せ字を送り返すと 400、または本物が消える

信頼度（`/users/:id/reputation`, `/users/:id/renter-profile`）は「画面に載せる」のではなく
「ID を知っている場所（GPU 詳細・注文詳細）のレスポンスに埋め込んで独立ルートを消す」
形にした。製品はユーザー ID を画面に出さないので、ID を引数に取るルートは原理的に
到達できない。**到達できないルートを画面から呼ぼうとする前に、なぜ到達できないかを問う。**

### G. 規則が読む範囲の外に証拠があった — 「その判断材料はどこにあるのか」（第 3 回）

第 1 回の起点は「不変条件は金を見ているか、記録を見ているか」だった。第 3 回は同じ問いを
**証拠**に向けた。製品が下している判断を 3 つ選び、それぞれについて
「**その判断材料は、判断する側から見えるところにあるのか**」を問うた。3 件とも答えは
「見えていない」で、3 件とも金か秘密情報が動いていた。

| 主張 | 問い | 答え |
|---|---|---|
| 接続情報は「終了時に破棄する」（access-delivery.js） | **破棄しているのは誰か** | 終端へ遷移させる 8 経路のうち 3 本だけ。SLA 違反の自動終了・係争の返金裁定・係争の棄却・期限切れ注文の失効・係争の自動裁定の 5 本は、終わったレンタルの SSH 鍵を `orders.json` に残し続けていた |
| 「精算は実提供量に応じて行う」 | **借り手が /stop を押さなかった注文の実提供量はどこから来るのか** | どこからも来ない。期限切れ掃除は稼働実績を書かないので按分が測定値なしに落ち、**実提供 0 = 全額返金**。借りる → 使う → 押さない → 放置、で代金が全額戻る経路になっていた |
| 「プロバイダーのハートビート途絶を検出して自動終了する」 | **その判定材料はどこにあるのか** | プロセス内の Map だけ。再起動した瞬間に証跡が消え、箱が落ちている注文は二度と検出されない（借り手は死んだ GPU に全額払う） |

3 件とも、修正は「気をつける」ではなく**見える場所へ証拠を移す**形にした:

- 接続情報の破棄は 5 箇所への追記ではなく、`OrderRepository` の書き込みフック
  （`beforeWrite`）で「終端状態の注文は認証情報を持てない」を強制した。注文を書く経路は
  リポジトリしかないので、経路を数え上げなくても成り立つ。手書きの破棄 2 箇所は削除した
  （2 つの仕組みが並ぶと「書いた場所は守られている」という誤った安心が生まれる）
- 放置レンタルは、期限を「開始から 48 時間」の固定値から「予約終了 + 猶予」に改め
  （48 時間を超える正当な予約が稼働中に殺されていた）、掃くときに実提供割合を**必ず**書く。
  判断材料はプロバイダーが接続情報を渡していたかという一次証跡に置いた
- SLA 判定はスイープが最新ビートを注文へ書き戻し、セッションではなく注文を回す。
  ただし**プロセスが自分で観測していない証跡には起動時刻を下限に取る**。これが無いと、
  運営が 1 時間サーバを止めただけで稼働中の全プロバイダーが違反と判定され、
  責任の所在が逆転する

副産物として「注文が終わっているか」の定義が 2 箇所に複製されていた
（`TERMINAL_SESSION_STATUSES` / `CREDITABLE_ORDER_STATUSES`）ので
`src/orders/order-status.js` に一本化した。値が同じなのは偶然ではない。
セッション回収・金の計上・秘密情報の破棄は、すべて同じ一つの問いに帰着する。

**テストが緑だったことは反証にならない。** `active_timeout` の按分は、合成した
`deliveredRatio` を渡すテストで守られていた。実データがその値を持たないことは、
テストからは見えない。単体テストは「与えた入力に対する出力」しか検証しないので、
**入力が現実に到達するか**は別に確かめる必要がある。

### H. 文書は正しく、製品が嘘をついていた（第 4 回）

第 3 回は「判断材料はどこにあるのか」だった。第 4 回は矛先を**製品が利用者に見せている
断定**へ向けた。UI の文字列から「済み／保証／確認／検証／実測」を機械的に拾い、
一つずつ「**誰がそれを確認したのか**」を問うた。

**1. 「スペック: 実測検証済み」（緑バッジ）— 確認したのはプロバイダー自身だった。**
照合しているのは「プロバイダーが申告したスペック」と「プロバイダーが同じリクエストで
送ってきたレポート」で、署名は長さ 8 文字以上か、証明書チェーンは配列が空でないかしか
見ていない。`firmwareIntegrity` はプロバイダーが `true` と書く真偽値である。実機
ベンチマークはどこにも無い（サーバは他人のマシンでコードを実行できないので、
ベンチマーク API は以前この理由で削除した）。自作 JSON を添えるだけで買えたもの:

  1. 緑の「実測検証済み」バッジ
  2. 性能スコアの裏付け（confidence: reference → attested）
  3. 未知型番のスコア上限解除と、`sort=recommended` のアテステーション枠（総合の 10%）満点

ここで重要なのは、**仕様書と README は正しかった**ことである。「『検証済み』と称して
よいのは申告の内部整合性まで」と明記されていた。規定は存在し、製品がそれを破っていて、
破りを検知するものが何も無かった。文書を守るのは文書ではない。

直し方は文言の書き換えではなく、証拠の強さを型で持たせること（`trustLevel`）。
上の 3 つの利得はすべて `hardware_attested` を要求し、現在の検証器はそれを返さない。

**2. 「GPU 利用率の記録から、実際に計算処理が行われたことを確認しました」— 記録が無い。**
ゼロ負荷検出はハートビートの任意フィールド `utilizationPct` を両者から集めて突き合わせる
設計だが、**製品の中に送る者がいない**。ブラウザは GPU 利用率を測れないので
`public/js` のハートビートは送らない（送れない）。したがって判定は常に `no_data` で、
検出は一度も発火せず、3 つの UI バナーはどれも表示され得ない。

この経路は元々 `detectZeroLoad()` が「部品はあっても稼働していない」状態を直すために
書かれたものだった。**同じ形を一段上で繰り返していた。** 受け口を結線したことを
「結線済」と書いてしまったのが誤りで、結線したのは*受け口*であって*供給*ではない。
供給を作るにはプロバイダー側のエージェントが要る（ベンチマーク API を消したのと同じ壁）。
仕様書をその通りに直し、UI の断定を「両者の申告が一致した」という事実の記述に改め、
**文書と配線がずれたら落ちる検査**を置いた（供給が付いたのに「発火しない」と書いたまま、
あるいは供給が無いのに「結線済」に戻った、のどちらでも落ちる）。

### I. 監査ログの「改ざん検知」は起動時の一回しか見ていなかった（第 5 回）

第 4 回は製品が利用者に見せる断定を疑った。第 5 回は矛先を**自分自身を検証する仕組み**
へ向けた。この製品でもっとも強い保証の一つ、監査ログの HMAC ハッシュチェーンである。

`src/security/audit-anchor.js` のヘッダは「`audit-log.js` は HMAC ハッシュチェーンで
tamper-evident」と書いている。**問: tamper-evident は誰かが見て初めて意味を持つ。
誰がいつ見るのか。**

答えは「起動時に一度だけ」だった。`appendAuditLog()` はプロセス内にキャッシュした
`prevHash` から次のハッシュを計算するだけで、ディスク上の実ファイルを見直さない。
チェーン全体を読み直して検証する `verifyAuditLogIntegrity()` は、その起動直後の
キャッシュ初期化（`_getOrInitPrevHash`）の中で一度呼ばれるだけで、**それ以降の呼び出し元は
本番コードのどこにも無く、テストからしか呼ばれていなかった**（grep で確認した）。

つまり、コンテナ内 RCE・ログボリュームの sidecar・共有ボリューム経由でログファイルを
直接書き換える改ざんが起きても、プロセスは気づかない。次に自分が書き込むときは
キャッシュした `prevHash` から素直に続きを計算して `.hash` を上書きするので、
チェーンは「正常」に見え続ける。次にプロセスを再起動するまで、誰も気づけない。

これは第 3 回・第 4 回で見つけた欠陥とまったく同じ形をしている。規則
（「改ざんを検知する」）は正しく実装されているのに、**それを実行する者が製品の中に
いなかった**。第 4 回のゼロ負荷検出は「供給が無い受け口」だったが、今回は
「呼び出し元が無い検査関数」である。

直し方は、既存のテストが呼んでいた関数をそのまま本番の定期ジョブに載せることだった。
`src/security/audit-integrity-monitor.js`（`earnings-sweeper.js` / `anchor-scheduler.js`
と同型の setInterval + 再入ガード + unref）が `checkIntegrity()` を 5 分ごとに回す。

検出しても**自動修復・自動停止はしない**。稼働中の検出は誤検知（ボリュームの一時的な
読み取り不整合等）を排除できず、それだけで製品を落とすのはこのコードベース全体が
繰り返し選んできた方針——「断定できない異常は記録・通知に留め、資金や可用性を
自動で動かさない」——に反する。検出は `auditIntegrityHealth()` として状態に残り、
一度でも検出したら人が調査するまで戻らず、外部チャネルへ 1 回だけ通知し、`/ready` を
503 に落とす。ここでも「自動で直さない」を選んだのは、ゼロ負荷検出や放置レンタルの
精算（第 3 回）で採った態度と同じである。

### J. 「未対処」は未検証だったのか——残る 4 件を Musk の①で問い直す（第 6 回）

第 1〜5 回は製品の主張を疑ってきた。第 6 回は**この点検自身の主張**を疑った。
「未対処」として並べてきた 4 件は、本当に検討済みの境界線か、それとも
「難しそうだから」で止まった未検証の言い訳か。マスクのアルゴリズムの①（要件を疑う）を、
todo リストそのものに適用した。

**1. 実送金の手動承認。** 問い直した結論: **これは欠陥ではなく正しい設計である。**
出金は「プロバイダが自分の BOLT11 invoice を提出 → 運営が申請額との整合を確認 →
実行」という形で、金額の大小に関わらず自動承認する安全な部分集合は無い——
乗っ取られたアカウントが自分の残高の範囲で送金先を差し替えるだけでも実害が出る。
自動化すべき要件ではないと判断し、todo から外す。現状の
「サーバは払えるが人が実行する」設計を維持する。

**2. アテステーション Mock。** 実機検証（nvtrust）には NVIDIA の Confidential Computing
SDK と対応 GPU ハードウェアが要る。このセッションの環境には存在せず、代替も無い。
文書は「Mock であり過大主張はしていない」で正確（第 4 回で `trustLevel` により
二重に保証済み）。継続監視以外にやることが無い項目として確定する。

**3. hold invoice エスクロー未結線。** 一段深く検証し直した。「`lnAdapter` を渡して
いない」という記述は正しいが不十分だった——**渡すだけでは動かない**。
`escrow-service.js:create()` は `preimage`/`preimageHash`/`providerInvoice` を
一切生成・保存しておらず、`marketplace-service.js:openOrderEscrow()` も
`invoice: null` で開設するだけである。`reveal_preimage`/`cancel_invoice` は
`ctx.preimage`/`ctx.preimageHash` が常に `undefined` のまま `lightning-service.js` の
実装済みメソッドへ渡ることになる。実際に必要なのは「アダプタの接続」ではなく、
**LND の `AddHoldInvoice`（`invoicesrpc`）で実際に hold invoice を発行し、借り手の支払い
フローをそこへ差し替え、invoice-poller に ACCEPTED 状態を教える**という、決済フロー
本体の再設計に近い作業だった。`tests/payments/no-unledgered-money.test.js` が
「本番はどこも lnAdapter を渡さない」ことを固定しており、この検証で見つかった
不足（preimage/invoice 生成の不在）を踏まえれば、そのガードは正しい位置にある。
ARCHITECTURE.md に詳細を追記した。今回のスコープには含めない——
決済の生命線（Lightning invoice → payout-ledger）を 1 本に保つ判断を優先する。
**この項目だけは「未検証の言い訳」ではなく「検証してより深い理由が見つかった」に
昇格したが、依然として未対応であることに変わりはない。**

**4. JSON データ層に複数レコードのトランザクションが無い。** 具体的な未発見のバグを
探したが、今回の点検で新たに見つかったものは無い。既知のリスク（台帳の二重計上・
注文と決済の整合）はすべて `createUnique`/`updateIf` の単一ファイル原子性で個別に
閉じている（第 1〜5 回で扱った箇所を含む）。JSON ファイルという保存方式を選んだ
時点で一般解が無いことは README の「できないこと」に明記済みで、過大主張はない。

結論: 4 件のうち 3 件（1・2・4）は、検討した結果「今は正しくやることがこれ」という
確定した判断であり、todo ではなく**恒久的な設計上の境界線**として扱うべきだった。
残り 1 件（3）は本当に未完成の機能だが、以前の記述より正確な理由が今回判明した。
「未対処」という言葉は、上記のうち①②④には適さない。**製品を「完成」させるとは、
すべてを実装し尽くすことではなく、残っている境界のすべてに理由があり、
その理由を自分で確かめてあることである。**

### K. 「未完成」自体を一段深く掘る——見た目は完成していたコードがもう一つ壊れていた（第 7 回）

Stop hook が「hold invoice エスクローは本当の未完成のままだ、②削除か③単純化を
実行せよ」と指摘した。①を再訪した第 6 回の結論（preimage/invoice 生成が無い）を
そのまま受け入れず、**②削除の前提として「本当にこれ以上分解できないほど掘ったか」**
を確かめ直した。

第 6 回は「`lightning-service.js` は `settleHoldInvoice`/`cancelHoldInvoice`/
`payInvoice` を実装済み」と書いていた。**問い直した: その「実装済み」は検証済みか。**

答えは否だった。`settleHoldInvoice()`/`cancelHoldInvoice()` は `this.lnd.settleInvoice(...)`
/ `this.lnd.cancelInvoice(...)` を呼ぶ。だがこの 2 つの RPC は LND の **invoicesrpc**
（`invoices.proto`、`lnrpc.Lightning` とは別サービス）が提供するもので、
`connectToLND()` が `protoLoader.load()` で読み込むのは `proto/lightning.proto` の
`lnrpc` パッケージだけだと確認した（grep で 1 箇所のみ、`.lnrpc` で終わることを確認）。
Mock LND（`setupMockLND()`）にも `settleInvoice`/`cancelInvoice` という名のメソッドは
無い。つまりこの 2 つは**本番でも Mock でも、呼べば必ず
`TypeError: this.lnd.settleInvoice is not a function` で落ちる**——第 6 回で見つけた
「preimage/invoice を生成する経路が無い」とは別の、もう一段下の欠落である。

`tests/payments/escrow-service-ln-wiring.test.js` がこれを見逃していた理由も特定した:
そのテストは `lightning-service.js` を一切使わず、`src/payments/ln-adapter.js` という
**独立したテスト用の代役**（`settleHoldInvoice` 等を単に記録するだけの Mock）を注入して
いる。だから「アダプタを渡せば正しく呼ばれる」ことは検証できていても、
「**実物のアダプタが実際に動くか**」は一度も検証されていなかった。見た目が完成した
コード（メソッドが存在し、それらしいロジックがある）が、実際に呼ばれる場面が
一度も無いまま放置され、壊れていることに誰も——このレビュー自身も第 6 回までは
——気づけなかった。

②削除は実行しなかった。理由: このコードは現在無害（呼び出す経路がどこにも無いので、
実行時に実害は出ない）で、`invoicesrpc` を正しく実装するには実機の LND に対して
検証できる環境が要る（プロトコルレベルの gRPC サービス定義を推測で書くのは、
金銭を扱うコードとして無責任）。代わりに実行したのは、このコードベース全体で
繰り返してきた選択——**断定できないなら、少なくとも失敗の理由を分かる形にする**
——である。`settleHoldInvoice`/`cancelHoldInvoice` は呼ばれた瞬間に
「invoicesrpc が読み込まれていないため」と名指しして失敗するようにした
（`_requireInvoicesRpc()`）。これは「④加速する」（同じ問題を次は人が思い出さなくても
気づける）の実行にあたる: 将来 preimage/invoice 生成側を直した人が、次にこの欠落へ
到達したとき、原因不明の TypeError ではなく理由を読める。

### L. ④加速では終わらせない——要件そのものを疑い、②削除を実行する（第 8 回）

Stop hook は第 7 回の「④加速（ガードで留める）」を明示的に拒否した:
「hold invoice エスクローは依然として本当の未完成のままだ。完成には
(1) ②削除の実行、(2) ③単純化の実行、(3) invoicesrpc を実機 LND 検証込みで
実装するかのいずれかが要る」という指摘だった。第 5〜7 回は「どう直すか」を
問い続け、「これは直すべき要件なのか」を一度も問い直していなかった。
①要件を疑う、をコードではなく**要件そのもの**に向け直した。

**問い: hold-invoice/HTLC エスクローは、この製品にとって何のための機構か。**
答え: 「運営を信頼しなくても資金が守られる」ためのトラストレス機構である。
HTLC は preimage を公開しない限り運営が資金を得られない構造にすることで、
運営の善意に依存せずに「配達されたら払う」を保証する。

**問い: この製品はどういう決済モデルか。** 答え: 全体を通して custodial である。
借り手は運営の Lightning ノードへ直接入金し、資金はいったん運営が預かる。
プロバイダへの払い出しは `payout-ledger.js` の台帳を経由し、運営が手動で
実送金して txid を記録する（README.md「意図的にそうしている設計」、
本書 J-1 で既に検討済みの確定判断）。GPU アクセスの受け渡しも運営が仲介し、
係争の裁定も admin が行う。つまり本製品は**運営を信頼する前提の上に全体が
組まれている**。

**問い: トラストレス機構を custodial 設計の上に足すと何が起きるか。** 答え:
何も変わらない。hold invoice の preimage を公開しても、資金は運営に入るだけで
（本書 J-3・K で確認済み）、プロバイダへの支払いは結局、台帳を経由する
別建ての送金になる。エスクローが守るはずの「運営を信頼しなくてよい」という
性質は、決済フローの他のどの部分にも存在しない。**要件として矛盾している**:
一部だけをトラストレスにしても、全体が custodial である以上、借り手も
プロバイダも結局運営を信頼するしかない。

**問い: 実害はどれだけあったか。** 答え: 二重の設計リスクがあった。
(1) `payout-ledger.js` と `escrow-service.js` は独立に同じ
`computeSettlement()` を呼んでおり、同じ注文に 2 つの異なる精算計算経路が
存在した（`payout-ledger.js:settlementForOrder()` は SETTLED escrow があれば
それを優先する分岐まで持っていた——「正」とすべき金額が 2 つ存在する状態）。
(2) 実注文でこの経路が使われたことは一度も無い（本番の呼び出し側は
`lnAdapter` 無しで `createEscrowService()` を生成しており、第 5 回で確認済み）。
つまりこの機構は、直しても製品に新しい能力を何も追加しない一方、
精算ロジックの二重化という実在のリスクだけを持ち続けていた。

**結論・実行（②削除）**: 要件として成立しないと判定し、hold-invoice
エスクロー/検証の合成層を丸ごと削除した。
`src/payments/escrow-service.js`、`escrow-state-machine.js`、
`action-executor.js`、`ln-adapter.js`、`src/db/json/EscrowRepository.js`、
`src/verification/verification-service.js`、
`src/db/json/VerificationRepository.js` を削除。`src/api/routes/marketplace.js`
の `/escrow/*` 全ルートと `adminOnly`/`escrowErrorResponse` を削除し
`POST /quote` のみ残した。`src/api/routes/index.js` の
`/admin/escrow`・`/admin/verifications/*` を削除。`src/marketplace/marketplace-service.js`
と `src/marketplace/default.js` を `quoteGpu` のみに縮小。
`src/utils/order-expiry.js`・`src/api/routes/order/index.js` の全エスクロー
連携フック（SLA スイープ、`GET /orders/:id/payment` の escrows フィールド、
admin PUT cancel、DELETE、reject、係争裁定 refund/uphold、`/stop`
自動解放）を削除。`lightning-service.js` の `settleHoldInvoice`/
`cancelHoldInvoice`/`_requireInvoicesRpc`（第 7 回で追加したガードごと）を
削除。`payout-ledger.js` の escrow-settlement 優先分岐を削除し、
`settlementForOrder()` を支払い実績ベースの計算 1 本に単純化（③単純化も
同時に実行）。`work-verifier.js` の純関数群は `utilization-collector.js` が
引き続き使うため削除していない。

これは「①要件を疑う→成立しないと結論する→②削除する」という手順を、
コード実装の細部にではなく機構の存在理由そのものに適用した結果である。
第 5〜7 回がやっていたのは「壊れた部品をどう直すか」で、実際に必要
だったのは「この部品はそもそも要るのか」だった。

### M. 削除の連鎖を最後まで辿る——死んだ経路が運んでいた「生きた値」（第 9 回）

第 8 回の削除のあと、一般則 4（削除は連鎖する）に従って「呼び出し元を失ったもの」を
全数調査した。モジュール単位で孤立したものは無く、関数単位で `work-verifier.js` の
`shouldAudit`/`outputsMatch`/`ternaryConsensus`（再実行監査。別プロバイダへの再投入経路は
製品に無い）と、`spot-tier.preemptionSettlement` の戻り値の半分（`opts`・`slaUptimePct`）が
呼び手を失っていた。前者は②削除、後者は③単純化（`preemptionDelivery` に改名し
`{deliveredSeconds, deliveredRatio}` だけを返す）で片付く——はずだった。

**問い: 戻り値のうち、生き残った呼び手は何を読み、それをどこへ渡しているのか。**
答え: `order-expiry.finalizePreemptedOrders()` は `deliveredSeconds` だけを注文に書き、
按分値 `deliveredRatio` はログに出すだけだった。**問い: では精算は按分値をどこから得るのか。**
答え: `payout-ledger.deliveredRatioOf()` は注文の `deliveredRatio` と `usageStats` しか読まない。
中断終了で両方とも無いと「中断終了・測定値なし」＝提供ゼロとして扱う（fail-safe として
意図された分岐）。つまり**中断で終わった spot 注文は、プロバイダへの支払いゼロ・借り手へ
全額返金**になっていた。借り手の画面は「実際に提供された時間分のみ課金」と表示していた。

按分値を実際に金額へ変換していたのはエスクローの `settle()` だけで、そのエスクローは実注文で
一度も使われていなかった。**死んだ経路が、生きた値の唯一の運び手だった。** 既存テストの
名前は「finalizes with strict pro-rata」だったが、中身は `deliveredSeconds` を見るだけで、
精算額までは一度も見ていなかった。仕様書も「最低課金を効かせない従量按分での精算 ✅」と書いていた。

修正: 中断の確定経路 2 本（猶予切れのスイープ、借り手の早期 `/stop`）が
`preemptionDelivery` の値を注文の `deliveredRatio` に書く。テストは台帳の精算額
（課金は約半分・プロバイダ支払い > 0・課金＋返金＝支払額）まで検査し、書き込みを
外すと 2 件とも落ちることを確認した。

同じ全数調査で、以前から呼び手の無かったものも片付けた: `lightning-service.js` の
`getPendingPayments`/`openChannel`/`closeChannel`/`getNodeStats`（とそれにしか使われて
いなかった `getChannelBalance`/`getChannelStats`——削除はここでも連鎖した）、importer ゼロの
`src/gpu/metrics.js`（687 行）と `src/api/webhook.js`。後者は probe32 が「live な通知経路」
として SSRF ガードを検査していたが、ルータはどこにもマウントされておらず、しかも素の axios
（リダイレクト追従あり）で送っていたので probe66 のリダイレクト迂回対策も入っていなかった。
**テストが守っていたのは到達不能なコードで、実際に動く `notifier.sendWebhookNotify` は

最後に、ユーザー確認のうえ担保ステークを削除した。**問い: `stake` は誰が書くのか。**
答え: 誰も（`addStake`/`setStake` は本番から一度も呼ばれない）。全員 stake=0 のため
`stakeFactor = minStakeFactor = 0.5` で固定され、**全スコアが一律に半分**、tier の閾値

担保ステークはエスクローと同じくトラストレス機構で、custodial 設計では成立しない（第 8 回と同じ

## この点検から得た一般則

1. **不変条件は、それが読む範囲の外を守れない。** 帳簿の突き合わせは帳簿しか見ない。
   金を守りたいなら「金が動く経路」の側を構造的に狭める必要がある。
2. **列挙は必ず古くなる。** 再発防止の検査を書くときに、消したばかりのものを手で
   並べてはいけない。導出できる形にしないと、書いたその日から漏れる。
   （この文書の B 節はその失敗の記録である。）
3. **「呼ばれている」と「実行されている」は違う。** `executeActions()` は呼ばれていたが、
   `lnAdapter` が無いので即 return していた。呼び出しの存在を配線の証拠にしない。
4. **削除は連鎖する。** 1 本のルートを消すと、そのために存在していた 3 モジュールが
   呼び出し元を失った。②を飛ばして③以降をやると、この連鎖が起きない。
5. **規則は、それが読めない証拠を使えない。** 「終了時に破棄する」「実提供量で按分する」
   「途絶を検出する」はどれも規則としては正しく、証拠がプロセス内の Map や
   誰も書かないフィールドにあったために静かに空振りしていた。規則を足すときは
   **その判断材料が、判断する時点で、判断する側から見えるか**を必ず問う。
6. **テストが緑であることは、実データがその経路を通る証拠ではない。** 合成した入力で
   分岐を守っていても、本番でその入力が生成されないなら分岐は一度も通らない。
7. **文書を守るのは文書ではない。** 仕様書と README は「『検証済み』と称してよいのは
   申告の内部整合性まで」と正しく書いていた。それでも製品は緑の「実測検証済み」を出して
   いた。honesty は宣言ではなく、破れない形（型・検査）にして初めて維持される。
8. **受け口を作ることは配線ではない。** 入力を受け取る API を足した時点で「結線済」と
   書きたくなるが、**その入力を誰が生成するのか**を答えられないなら、その機能はまだ
   動いていない。「呼ばれている ≠ 実行されている」の供給側の対。
9. **検証関数は、検証されて初めて役に立つ。** `verifyAuditLogIntegrity()` は正しく
   実装され、テストにも守られていた。それでも本番で呼ぶ者がいなければ、起動の瞬間の
   健全性を確かめただけで終わる。「テストで呼ばれている」を「本番で実行されている」の
   証拠にしない——3 の系だが、今回は関数自体が製品の安全機構である分、見落としの
   代償が大きい。
10. **「未対処」は結論であって前提ではない。** todo リストに載っているという事実は、
    それが本当に todo である証拠にならない。「難しそうだから保留」と「検討した結果
    やらないと決めた」は書いた本人にも区別が付きにくいが、読む人にはまったく違う情報
    になる。①要件を疑う、はコードだけでなく自分がこれまで書いた「未対処」リストにも
    向けるべき問いだった。
11. **「実装済み」と書いた自分の言葉も、コードと同じ疑いの対象にする。** 独立した
    Mock を注入するテストは「配線が正しいか」は検証できても「実物が動くか」は
    検証できない。第 6 回はコードを読んで「実装済み」と結論したが、実際に
    実行させてはいなかった——テストを書いた本人でさえ、この区別を見落とし得る。
    掘り下げは一度で終わりにせず、「これ以上分解できないか」を毎回自分に問い直す。
12. **「直せば直るか」の前に「これは要件か」を問う。** 壊れた実装を掘り下げて原因を
    特定し、ガードを足して④加速するのは、それ自体は正しい手順に見える。しかし
    ①要件を疑う、を飛ばして④に進むと、**存在しなくてよい機能を直し続ける**
    という別の形の無駄が生まれる。今回は、機構の目的（トラストレス性）と製品の
    設計原則（custodial）を照らし合わせるだけで、3 回分の深掘り（第 5〜7 回）が
    ①一問で②削除に置き換えられることが分かった。「直せるか」ではなく「直す価値が
    あるか」を先に問う。
13. **死んだ経路が、生きた値の唯一の運び手であることがある。** 削除の連鎖を辿るときは
    「何が呼び手を失ったか」だけでなく「消した経路が何を運んでいたか」を問う。
    エスクローは使われていなかったが、spot 中断の按分値はそこにしか流れておらず、
    結果として一度も金額に反映されていなかった。同じく、書き手のいない入力（stake）は
    既定値に固定され、その既定値が製品の数字（全員のスコア）を黙って歪める。
    どちらも順位や状態遷移のテストは緑のままで、**金額・表示値そのものを検査して初めて見える**。
